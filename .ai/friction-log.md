# Friction Log

Raw material for the `review-agent-os` role. Whenever something in the agent-OS,
the docs, or the workflow **slowed you down, misled you, or caused rework**, append
one line here before you finish your task. Be specific and point at the file.

This is not a bug tracker for the product — it is a log of friction in *how we work*.
Newest at top. The review role mines this list and prunes entries once addressed.

Format:

```
- YYYY-MM-DD [role] what was wrong/misleading + where (file:line or path)
```

## Entries

- 2026-05-31 [run-next-phase/P24] The p23-shoelace-adapter E2E test checked `a.webapp-button, button.webapp-button` even though commit 100b774 (the P23 follow-up) already rendered buttons as `sl-button`. The test was passing before P24 because the e2e server hadn't been rebuilt since before 100b774 — a stale server masked the stale selector. P24's shell removal exposed it. Lesson: E2E specs that assert element classes should be updated in the same commit that changes those classes; otherwise they silently pass against a stale server.
- 2026-05-31 [fix-bug] P23 was marked `done` although its own acceptance criterion ("the customers-crud example renders with Shoelace components") was not met: `webapp.js` only routed *containers* through the adapter (sl-card); buttons/inputs/tables/text still emitted the old `webapp-*` markup, so the served page loaded Shoelace from the CDN and never used it. The validation passed on adapter unit tests + a custom fixture rather than asserting the *served HTML* contained `sl-*`. Lesson: a "renders with X" criterion must assert against the real served output, not a proxy. Fixed by routing button->sl-button and input->sl-input (text/table stay semantic HTML — Shoelace 2.x has no element for them). Note: the adapter's KIND_TO_SHOELACE still maps text->sl-format-text and table->sl-table, neither of which is an appropriate/real general element — those map entries are misleading and should be corrected or removed.
- 2026-05-31 [evolve-roadmap/archival] `docs/agent-roadmap-archive.yaml` was committed as broken YAML across multiple phases: archive entries appended by the orchestrating sub-agents (P14, P16a-d, P17, P20a, P20b, P21, P22, P23) sat at column 0 instead of 2-space under `phases:`, so the file did not parse at all (`end of the stream or a document separator is expected`). No step validates the archive YAML after append, and `run-next-phase`'s archive-format example does not show the required 2-space indent under `phases:`. Two consequences: (a) a concurrent archival edit got silently clobbered by the orchestrator's commits, and (b) nobody noticed the archive was unparseable. Fix applied here: normalized all entries to 2-space. Real fixes: add a YAML-parse check to the archive step, and an explicit indent note in the archive-format section. Also: never run two agents writing the same roadmap files at once — coordinate or wait.
- 2026-05-31 [run-next-phase] P23 again hit the red E2E baseline (same as P21/P22). Root cause now diagnosed: the suite shares ONE Node-RED instance, and `layout-apps.spec.ts` deploys a demo app over the shared `customersApp` flow (its `afterEach` restore does not reliably persist), so every alphabetically-later spec that needs `customersApp` (`p21` detail, `p23`, etc.) fails with "Unknown app 'customersApp'". The failures vary run-to-run (p15, second parent-selector) which is classic shared-state flakiness, not phase regressions. Workaround in P23: the spec re-deploys `examples/customers-crud/flow.json` in `beforeEach` so it is order-independent. A real fix (per-spec isolation, or restoring the baseline flow in a global afterEach/projects setup) belongs outside any single phase.
- 2026-05-31 [run-next-phase] P21 inherited a red E2E baseline: 8 of 23 Playwright specs (customers-crud action flow + 7 editor parent-selector/mount/p16d specs) already failed on the untouched commit. `validation.md` step 1 says "fix every failure" but gives no guidance for pre-existing failures outside the current phase's scope — had to stash+rebuild to prove they were not regressions, which cost a full E2E baseline run. A documented "known-red baseline" marker or a green-baseline gate before phase start would avoid this.
- 2026-05-31 [run-next-phase] P22 needed a state-changing event to validate the client round-trip, but post-P20a `applyPreviewAction` no longer changes state for typed ui-action nodes: a typed action with no `targetMode` falls into the "emit only, wiring handles the rest" branch BEFORE any of the legacy CRUD branches (open dialog / save / navigate), so the customers-crud preview no longer opens dialogs, saves, or navigates. This is the same pre-existing preview-action bug spun off in P21; it forced P22 to ship a dedicated fixture flow whose button ids equal handled action names and whose actions carry no actionType. Worth a real fix in the spun-off bug task so the customers-crud example is interactive again.
